## Status vocabulary and current-candidate note

- `EXECUTED / PASS`: the cited executable check ran and the cited retained evidence records success.
- `IMPLEMENTED / STATIC_EVIDENCE`: the repository source or manifest supports the claim, but the row does not assert a complete dynamic proof of absence.
- `WORKTREE_UNIT_PASS`: the cited unit suite passed in the current source tree; this does not substitute for a final clean-checkout receipt or refreshed browser/media evidence.
- `COMMIT_SCOPED_PASS`: a clean-checkout receipt applies only to the exact commit and tree named by that receipt.
- `UNKNOWN / NOT_CLAIMED`: the repository has no evidence sufficient for the broader claim.
- `NOT_EXECUTED`, `NOT_PUBLISHED`, or `NOT_DEPLOYED`: the external action has not been evidenced.
- `USER_GATED`: explicit user authorization is required before the action.

## Release-time refresh gate

Before a later README, Devpost form, release, or judging handoff uses an unqualified `PASS`, rerun the exact final commit and update only claims supported by fresh evidence:

1. run the complete unit suite and deterministic CLI transform;
2. run the loopback HTTP checks;
3. regenerate `artifacts/browser-qa.json`, both screenshots, and the WebM from that same final tree;
4. verify 39/39 browser checks (or document and explain the new exact count), console/page errors, duration, dimensions, codec, and final hashes;
5. clone the final commit into a new checkout without hard links and repeat the release gates;
6. record the exact final commit/tree in a new receipt;
7. leave all external rows above unchanged until their separately gated actions actually occur.
